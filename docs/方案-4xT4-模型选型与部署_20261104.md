# 4×T4 上跑通「图片 → 可编辑 PPTX」：模型选型与部署方案

编写：2026-11-04
适用：`36.134.45.38`（32 vCPU / 251 GB / 4×Tesla T4 15 GB / `/data` 818 GB 空闲）
现有：`image2ppt-vision:0.2.1` 已跑在 `127.0.0.1:18761`，CPU 推理（PP-OCRv4 + SAM）

---

## 0 先把一件事说清楚：这条链路里模型只占一环

你的服务已经把**几何**管死了，这是它比 image2ppt.com 更结实的地方。看 `validate_element_plan` 的实际代码：

- `text_decisions[].id` 必须是 OCR 给的真实 ID，`bbox` 从清单里抄，模型编不出来；
- `objects[].candidate_id` 必须落在 OpenCV 候选集里；
- 每个 OCR ID 只能有一个处置决定，不能漏、不能重；
- 原生文字和切片里的文字不能重复（`raster_text_conflicts`）。

**所以模型不该被用来出坐标。** 模型只做四件事：**分类、分组、属性、z 序**。

对照你贴的那张图，真正缺模型的只有三处：

| 阶段 | 缺什么 | 严重度 |
|---|---|---|
| ① 页面理解 / 规划 | 没有人把 OCR+候选变成 `ElementPlan/2`（`reconstruction_requires_plan: true` 就是这句话） | **致命**，不补就全链路空转 |
| ② 背景净化 / 擦字 | 没有 inpainting（路线图里写着"自动擦字与背景修复"未实现） | **高**，这是 image2ppt 成品那 55% 切片和残影的根 |
| ③ 切块质检 | 没有"切片里是否还留着字"的自动检出 | 中，可后补 |

④ 文字测量（颜色/字重/字号/字体拟合）你已经有 `typography.py` / `font_plan.py`，⑤ 组装是确定性编译器，都不需要模型。

| 阶段 | 谁来做 | 具体选型 | 显存 | 现在有没有 |

## 2 为什么是 Qwen2.5-VL-7B

**它要对上的任务**：看一张 1672×941 的页面，读一份 inventory（可能有 100–300 条 OCR、几十个 CV 候选），输出一份严格 JSON。要求是中文好、小字能看清、结构化输出稳、长上下文不崩。

选它的理由：

1. **中文与密集排版**是它的强项，政务/技术类 PPT 的正文小字识别率明显高于通用 VLM；
2. **动态分辨率**，1672×941 不需要强行缩放，小字不糊；
3. **AWQ INT4 能在单张 T4 上跑**，权重约 5.5 GB，留得下 8–16k 上下文；
4. vLLM 原生支持，能开 guided decoding 强制 JSON Schema。

**T4 的三个硬限制必须先知道**：

| 限制 | 后果 |
|---|---|
| 计算能力 sm_75，**没有 FlashAttention-2**（要 sm80+） | vLLM 走 XFormers/Triton 后端，吞吐约为 A10 的 1/3 |
| **不支持 BF16 / FP8** | 只能用 FP16 或 INT4，别照抄网上 BF16 的配置 |
| 15 GB 显存 | 7B FP16（16 GB）单卡放不下，必须 INT4 或两张卡 TP=2 |

**升级路径**（如果镜像里能拉到更新版本，优先用新的）：Qwen3-VL 系列、InternVL3 系列在文档/版面理解上更强；`dots.ocr` 这类"版面+识别一体"的小模型适合替代 OCR 那一段，但要确认它输出的坐标粒度和你的 OCR ID 体系能对齐——对不上就不要换，你的契约依赖 OCR ID 做主键。

**32B 级别**：如果 7B 在疑难页上分类经常错，可以再加一个 Qwen2.5-VL-32B-AWQ，TP=2 横跨两张 T4（约 9.5 GB/卡），只对 7B 产出校验失败的页面跑第二遍。**不要全量上 32B**，T4 上单页会拖到 5 分钟以上。

## 3 显存与吞吐预算

### 方案 A：4 副本独立（推荐起步）

| 卡 | 服务 | 模型 | 权重 | 峰值占用 |
|---|---|---|---|---|
| T4-0 | planner-0 | Qwen2.5-VL-7B-AWQ | 5.5 GB | ~9 GB |
| T4-1 | planner-1 | 同上 | 5.5 GB | ~9 GB |
| T4-2 | planner-2 | 同上 | 5.5 GB | ~9 GB |
| T4-3 | planner-3 + erase | 同上 + Big-LaMa | 5.5 + 1.0 GB | ~11 GB |

并发 4，任意一张卡挂了不影响整体。

### 方案 B：2 卡 TP + 2 卡做 CV

| 卡 | 服务 |
|---|---|
| T4-0,1 | planner（TP=2，可用 7B-FP16 或 32B-AWQ） |
| T4-2 | erase（LaMa）+ 可选 CLIP |
| T4-3 | 备用 / 第二批副本 |

质量更高、并发更低。**建议先 A 跑通，需要提质量再换 B。**

### 单页耗时估算（INT4、单卡 T4）

| 环节 | 估算 | 依据 |
|---|---|---|
| 图像编码 + prefill | 3–6 s | 约 1.3k 视觉 token + 2–4k inventory 文本 |
| 解码 1.5–2.5k tokens | 40–80 s | 4 GB 权重、320 GB/s 带宽、实测 30–40 tok/s |
| **单页合计** | **约 1–2 分钟** | |
| 12 页 / 4 并发 | **约 5 分钟** | 端到端不含编译 |

对比 image2ppt.com 的"秒级"：它是单次前向出一份扁平清单，你是多步可复核的链路。**这个方案卖的是"改得动"，不是"出得快"**，别在延迟上跟它比。

## 4 服务器上的部署拓扑

### 目录（全部放 `/data`，818 GB 够用）

```
/data/image2ppt-vision/
├── models/                      ← 已挂进容器作 /models
│   ├── qwen2.5-vl-7b-awq/       （新，约 5.5 GB）
│   ├── big-lama/                （新，约 200 MB）
│   └── （现有 PP-OCRv4 + SAM 不动）
├── data/                        ← 现有任务数据，不动
├── services/
│   ├── planner/                 （新：FastAPI，包 vLLM 客户端 + Schema 校验）
│   ├── eraser/                  （新：FastAPI，包 LaMa）
│   └── compiler/                （新：Node + Artifact Runtime）
└── ops/compose.planner.yml      （新）
```

### 容器与端口（一律只绑 127.0.0.1，统一走 nginx ingress）

| 容器 | 端口 | 说明 |
|---|---|---|
| `image2ppt-vision-v1-api-1` | 18761 | **已有，不动** |
| `i2p-planner-0..3` | 18800–18803 | vLLM OpenAI 兼容接口，每卡一个 |
| `i2p-planner-gw` | 18810 | 你的 FastAPI 网关：取 inventory → 调 VLM → 校验 Schema → 轮询重试 |
| `i2p-eraser` | 18820 | LaMa，入图+掩码出 plate |
| `i2p-compiler` | 18830 | POST /compile，跑 `scripts/compose.mjs` |
| `i2p-ingress` | 18760 | nginx，按路径分发到上面几个 |

**不要复用 18761 的容器**：它 `pptx_compilation: false`、`network_inference: false`，是刻意设计成"不碰模型、不碰编译"的。前置一个 planner、后置一个 compiler，它的边界反而更清楚。

### vLLM 启动示例（T4 专用参数）

```bash
docker run -d --name i2p-planner-0 --gpus '"device=0"' --restart unless-stopped \
  -v /data/image2ppt-vision/models:/models:ro \
  -p 127.0.0.1:18800:8000 \
  vllm/vllm-openai:v0.6.6 \
  --model /models/qwen2.5-vl-7b-awq \
  --served-model-name planner \
  --dtype float16 \
  --max-model-len 16384 \
  --limit-mm-per-prompt image=1 \
  --gpu-memory-utilization 0.85 \
  --enforce-eager
```

要点：`--dtype float16`（T4 无 BF16）；`--enforce-eager` 规避 sm75 上的 CUDA Graph 问题；`--gpu-memory-utilization 0.85` 给图像编码留余量。**具体镜像版本按你实际拉到的调整，T4 支持看 vLLM 的 sm75 说明，别直接用最新版**。

### 模型下载

国内优先 ModelScope（`modelscope download`），HF 备用。下完核 `sha256` 再挂载——你现有的 `models-ready/manifest.json` 已经是这个规矩，沿用即可。

## 5 接口契约：planner 必须严格输出 ElementPlan/2

这是全篇最需要贴代码的地方。你的校验器 `validate_element_plan` 拒绝一切未知字段和越界值，**模型输出必须逐字段对齐**：

```jsonc
{
  "schema": "ElementPlan/2",
  "source_sha256": "<与 inventory 一致>",
  "image_size": [1672, 941],
  "background_color": "#FFFFFF",
  "objects": [
    {
      "id": "card-1",                       // [A-Za-z0-9_-]{1,70}，全局唯一
      "kind": "native_shape",               // 或 raster_asset
      "bbox": [24, 221, 524, 199],          // 源图像素坐标
      "z": 3,                               // 整数，非 bool
      "candidate_id": "cv-17",              // 可选，必须是 CV 候选
      "geometry": "roundRect",              // 13 种之一：rect/roundRect/ellipse/line/
                                            // chevron/pentagon/rightArrow/leftArrow/
                                            // trapezoid/parallelogram/hexagon/diamond/triangle
      "fill": "#E8F2FB",
      "fill_gradient": {"stops": [{"color": "#E8F2FB"}]},
      "line": {"color": "#73B9E8", "width_pt": 0.75}   // 0 ≤ width_pt ≤ 20
    },
    {
      "id": "icon-crane",
      "kind": "raster_asset",
      "bbox": [62, 224, 66, 59],
      "z": 4,
      "mask": "rect",                       // rect 或 ellipse
      "contains_text_ids": []               // 切片里还留着的 OCR ID
    }
  ],
  "text_decisions": [
    {
      "id": "ocr-042",                      // ← 必须来自 inventory.texts
      "bbox": [179, 235, 134, 30],          // ← 抄 inventory，不许改
      "text": "园区治理",
      "color": "#004B91",
      "action": "native",                   // 或 retained_in_asset
      "bold": true,
      "z": 20,
      "font_size_px": 30,                   // 1 ≤ px ≤ 400，不是 pt
      "font_family": "微软雅黑",             // ElementPlan/2 必填
      "font_latin": "微软雅黑",
      "font_confidence": 0.8,               // 0–1
      "font_evidence": "笔画等宽、无衬线、字面较大，与雅黑一致"
    }
  ],
  "limitations": []
}
```

**硬约束（模型输出后必须机器校验，错了就重试，最多 2 次）**：

| 约束 | 值 | 违规后果 |
|---|---|---|
| objects 数量 | 1–400 | 超限直接拒绝 |
| objects + texts | ≤ 500 | 同上 |
| 单个 raster 面积 | ≤ 页面 18% | 拒绝（注意：**满幅底图 100% 会被拒**） |
| OCR ID 覆盖 | 每条恰好一次 | 漏一条即失败 |
| id 格式 | `[A-Za-z0-9_-]{1,70}`，全局唯一 | 拒绝 |
| font_size_px | 1–400，有限数 | 拒绝 |
| 字体族 | 必须在服务端已验证目录内（雅黑/黑体/宋体/等线等） | 拒绝 |
| 原生文字 vs 切片文字 | 不得重叠 | 拒绝 |

**引导解码**：vLLM 开 `guided_json`（新版本叫 `structured_outputs`），直接把这个 Schema 塞进去，能省掉大半重试。字段名一个字母都不能错——`font_size_px` 写成 `fontSizePx` 就整份计划作废。

## 6 唯一需要的契约扩展：把"擦字"接进链路

这是我要提醒你的最关键一处。

看 `validate_element_plan` 第 93 行：**单个 raster 面积不得超过页面的 18%**。这意味着 image2ppt.com 那套"满幅去字底图 + 局部切片"的做法，**在你当前契约下根本表达不出来**——满幅底图作为 object 会被直接拒绝。

同时第 97、108 行：切片盖住的原生文字必须声明 `retained_in_asset`，否则判为冲突。于是你只能二选一：

- 整块画成原生（卡片渐变/阴影画不出来，必然掉真）；
- 整块保留文字在切片里（文字不可编辑，回到 image2ppt 之下）。

**要追平它的效果，需要一处最小扩展**（不动校验哲学，只放行一个受控通道）：

1. Plan 增加顶层字段 `background_image: {sha256, source: "plate"}`，编译器把它放到**幻灯片背景层**，不算 object，因此不受 18% 限制；
2. `raster_asset` 增加 `source: "original" | "plate"`，语义是"从哪里切"；
3. `raster_text_conflicts` 保持用**原图 OCR** 校验——这样"擦完再切"仍然保证切片底下没有能看见的字，只是允许擦干净了。

配套新增一个操作：

```json
{"operation": "erase", "asset_id": "<分析过的图>", "text_ids": ["ocr-001", "..."]}
```

产出 `plate.png` + `erase_report.json`（每块掩码、修复方法、残差指标）。这样擦字这件事就变成**可测量、可回归**的一步，而不是藏在切片里的黑盒。

## 7 分四步落地（每步都有验收数字）

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **P0（半天）** | 修那个停摆 9 天的 worker（`unable to open database file`），或先绕开队列用 CLI；跑通"人工 plan → reconstruct → 宿主编译" | 12 页出 PPTX，产物完整 |
| **P1（2–3 天）** | 上 LaMa，先把擦字做成离线脚本 | 擦净率：掩码区域残差 P95 < 阈值；肉眼无残影 |
| **P2（1 周）** | planner 上线（VLM×4 + Schema 约束 + 重试） | 计划一次通过率 > 90%；未知字段 0；18% 违规 0 |
| **P3（3–5 天）** | 编译容器 + 端到端编排 + 契约扩展 | 12 页全自动跑完，无用例回退 |

验收口径沿用上一轮质检那套，直接可比：**整页平均像素差、切片覆盖面积、字号档数、组合数、残影检出数**。image2ppt 成品的基线是：像素差 13.01、切片 54.8%、字号 76 档、组合 0、残影随页可见。**只要你的数字在"像素差 ≤ 10 且切片 ≤ 30%"这个区间，就已经赢了。**

## 8 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| T4 无 FlashAttention-2 | 吞吐约为 Ampere 的 1/3 | 接受；靠 4 副本摊并发 |
| INT4 对长 JSON 有掉点 | 计划字段错、截断 | guided decoding + Schema 校验 + 最多 2 次重试 + 失败落人工 |
| 16k 上下文装不下极端密集页 | inventory 被截断 | 先对 OCR 做按块分组（VLM 分批出对象），不要一次塞全页 |
| 字体可用性 | `resolve_font` 直接拒绝 | 沿用现有 `/fonts/manifest.json`，只允许已验证族 |
| Artifact Runtime 能否进容器 | 许可与体积 | 先在本机验证镜像内可加载；不行就让编译留在客户端 |
| 共用机器 | 显存被抢、`/` 只剩 41 G | 只绑 127.0.0.1；镜像都放 `/data`，别往 `/` 拉模型 |
| 单页 1–2 分钟 | 不适合交互 | 定位为批量/离线，前端做队列进度 |

---

## 9 明确不做

- **不做端到端扩散出 PPT**：不可控、不可编辑，等于换一种截图。
- **不让 VLM 出精确 bbox**：坐标一律来自 OCR / CV 候选，这是你契约里已经做对的事。
- **不上 BF16 / FP8**：T4 不支持，别浪费时间调。
- **不在 T4 上硬跑 32B 全量**：一次可以，批量会很惨。
