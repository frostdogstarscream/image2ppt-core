审查日期：2026-10-22

## 结论

建议保留该方向，继续作为影子规划/人工辅助工具演进，不直接升级为无人审核的重建执行器。

它把“如何尽可能拆开整页”转成“哪些区域值得原生化、哪些应保留图片”，并区分 can_rebuild 与 should_rebuild。这个方向与混合重建产品目标一致。下一阶段的重点不是继续增加三分类标签的一致率，而是验证具体拆分方案的可执行性、编辑收益、保真损失和实际成本。

这里的审查建议不是合并操作。本轮没有修改 GitHub 仓库、创建 PR、调用收费模型或上传用户页面。

## 1. 审查与实验边界

读取了固定提交中的区域规划文档、归档计划与人工决定，以及 region_plan、region_shadow、secure runner、API worker 和相关测试源码。没有把整个 vision 服务或仓库的所有功能视为已审计。

本地仅对 `parse_response()` 原样摘录执行了 7 个响应外层格式边界探针。严格 JSON 辅助函数按同一实现保留；决策校验使用不可达哨兵，保证探针只测试错误响应外层，并不冒充完整业务测试。

没有执行完整项目测试、远端模型请求、真实区域重建、Artifact Tool 渲染或 PowerPoint/WPS 编辑。

仓库记载的 8 个模型调用、P8 样板和误差指标，属于作者归档结果。本轮没有独立重复这些实验。原始请求、响应、裁图和 P8 样板没有公开，不能从当前公开材料独立复核全部像素结论。

## 2. 现有方案中值得保留的结构

当前主链是：

```text
已存在的页面/图片区域
→ inventory：裁块与启发式图像特征
→ prepare-llm：离线建立请求与输入绑定
→ secure runner：显式发起网络调用
→ apply-llm：解析返回、规则校验、合并本地人工决定
→ validate / score / report
```

`apply-llm` 的 apply 指生成规划记录，不是把规划应用到正式 PPT。模型响应不覆盖 region_id、bbox 和 human 字段；这些由本地数据合并。人工决定不发送给区域模型，当前报告保留 `shadow_only: true` 与 `human_acceptance: false`。

这些边界应继续保留。不能因为响应符合 JSON 或规则一致，就直接写进正式 deck。

## 3. 如何解读当前 7/8

归档记录：8 个区域响应通过校验，7 个三分类 decision 与当前人工决定一致。人工标签分布为 6 个 retain_module、1 个 hybrid、1 个 native。

因此，始终输出 retain_module 的简单对照，在这组样本上就是 6/8。7/8 的结果有探索价值，但只有 8 个同一批页面的选定区域，不能推导为普遍还原率或商业交付成功率。

更重要的是，当前 `score()` 只比较 `agent.decision == human.decision`。

### P5：相同 hybrid 标签，不是相同方案

人工记录：标题原生 + 仪表盘整图。

模型计划：标题、卡片、KPI、条形图、类别标签、数值、表格、单元格等原生；只保留状态标签和图标。

二者在三分类标签上相同，实际编辑范围和拆分风险明显不同。因此 7/8 应称为“路由标签一致率”，不能称为“具体重建计划一致率”。也不能仅凭发现 P5 差异，就擅自给所有计划重新计算一个精确正确率。

建议增加结构化人工标注：required_edit_targets、must_retain_targets、允许的部件及编辑字段、目标保真等级。评测至少区分过度拆分、拆分不足、保留范围和最终候选验收。

### P8：应保留失败经验，但不要形成过度保守的通则

作者记录中，模型建议 hybrid，样板完成后人工选择保留原图片模块；区域 MAE 约为原图片方案 8.6、hybrid 17.7。

这证明“模型认为有价值”和“当前执行器做出用户接受的结果”之间有距离。它没有证明所有表格加文本区域都应该保留图片。

该否决应绑定输入、输出大小、字体/渲染器、执行器版本、编辑需求和实际候选。MAE 是对照指标之一，不能单独充当可编辑性评分；也不要把误差约翻倍说成质量减半。

## 4. 自动采纳前的代码修正

### R1：请求—响应绑定没有闭合（建议优先修）

位置：`services/vision/src/image2ppt_vision/region_plan.py` 的 `prepare_region_job()`、`apply_jobs()`；`api_eval_worker.py`；`scripts/run_supervised_jobs_secure.py`。

当前 apply 重新核验 request.json 与 crop.png，但 `transport.response_sha256` 只是复制到结果记录，没有与实际 response.body 重新计算的哈希比较。

API worker 已记录 response_sha256 和 saved_response_sha256；接收层尚未使用它们完成文件核验。原测试夹具仅写 `{"status":"RECEIVED"}`，也期待 apply 成功，说明缺少响应哈希并不会阻断当前路径。

此外，prepare 记录 endpoint_sha256，但复用 job 时没有重新绑定 settings.json 中实际 endpoint；runner/worker 发送前也没有将实际 endpoint 与 RegionJob 的 endpoint_sha256 核对。这是本地文件错配/修改时的完整性边界，不是声称发生过泄露或外部攻击。

建议：

1. 在网络调用前执行统一 verify_job：核验实际请求字节、裁图、endpoint、模型、能力与 prompt 版本，绑定发送端配置。
2. transport 记录实际 request_sha256、endpoint_sha256、job/binding 指纹。
3. apply 核验 response.body 与 saved_response_sha256，并核验该响应所对应的实际请求。缺字段、错配或哈希不符拒绝采用。
4. 凭据回显/脱敏的响应继续按失败处理；不要把原始接收字节哈希误当成脱敏文件哈希。
5. 哈希用于完整性和版本关联，不等同于对可同时修改数据和清单者的签名认证。

应新增测试：更换 response.body 而不更新 transport、跨 job 交换响应、缺响应哈希、改变 settings.endpoint、正常未变更控制组。

### R2：异常 message 会逃逸既定错误处理

位置：同文件 `parse_response()` 和 `apply_jobs()`。

对 message 调用 `.get()` 前没有检查它是否为 dict。本轮原样函数探针中：

| 输入情况 | 实际异常 |
|---|---|
| 空 choices | ValueError |
| 重复 JSON key | ValueError |
| finish_reason=length | ValueError |
| message=null | AttributeError |
| message=[] | AttributeError |
| message=字符串 | AttributeError |
| tool_calls | ValueError |

apply 的响应异常分支只捕获 OSError/ValueError/TypeError。因此从调用代码推断，后三种外层格式可中断该批 apply，而不是只记录对应区域 INVALID_RESPONSE。本轮没有执行整个批处理链，不把这一推断写成批量实测。

建议分层检查 envelope/choices/choice/message/content 类型；将边界格式错误统一转成受控异常。新增“首个区域格式错误、后续区域仍正常记录”的批处理测试。不要通过一个无差别吞错的 except Exception 隐藏程序缺陷。

### R3：公开归档与 schema 不完全一致

`docs/region-shadow-llm/plans.llm.json` 的 planner 增加了 raw_artifacts。当前 schema 的 planner 为 additionalProperties=false，且未定义该字段。

建议把归档说明移到 README/sidecar，或发布明确的归档 schema，并给 validation 绑定被检文件的哈希。归档编辑前的 valid=true，不应当作编辑后文件的验证凭证。

这不是原始模型响应一定失败的证据，也不是要求公开敏感原始裁图。

## 5. 方案级改进

### 5.1 从标签走向可执行区域提案

当前 native_parts/retained_parts 是类别清单，没有把每个实例绑定到子区域、遮罩或明确的编译操作。例如多个 card/table/labels，执行器不知道具体指哪一块。

建议引入独立候选计划，记录子区域 ID、区域内坐标、内容证据引用、拟用原语、可编辑字段、清理/保留策略。不要直接放宽已有 SlideIR。

尤其区分：原生条形图形状可移动、文字可编辑，与存在数据系列的原生图表，不是相同能力。

### 5.2 提供编辑目标、实际能力和剩余预算

仅有裁图可以减少上下文，但不足以决定 should_rebuild。用户只改标题，与用户必须改表格数值，最优策略不同。

在不泄露人工答案的前提下加入：输出缩放比例、目标字号下限、编辑目标、当前后端能力指纹、当前页节点/图片/文本框数量、剩余额度。

当前 CAPABILITIES 是固定常量；建议由实际编译后端导出能力快照，而不是由规划模块独立维护一份“看起来支持”的列表。P8 的 78 文本框超过配置中的 52 警戒值，并不是自动违规，但说明需要页面级预算和验收，不能只看区域局部。

### 5.3 不把启发式图像特征当成 OCR 真值

当前 text_components / median_text_height_px 来自阈值暗像素的连通分量统计，不是已确认文字行/字形。边框、图表线条等也可能影响统计。

建议在字段命名和提示中明确这是启发式信息，按目标尺度归一化，单独评测它对决策的增益；不必因此立即强制引入 OCR。

### 5.4 以候选试编译裁决是否采纳

建议下一阶段状态：

```text
PROPOSED
→ VALIDATED_STRUCTURE
→ TRIAL_BUILT
→ VERIFIED / REVIEW_REQUIRED
→ ACCEPTED 或 REJECTED
```

为每个目标区域保留当前方案作 baseline，在独立修订中试编译候选，比较文字正确性、区域保真、有效编辑目标覆盖、残影/裁图污染、对象预算和实际耗时。只有通过策略或人工确认才合入正式页面。

模型 confidence 只是模型自报，不是经过校准的成功概率。

## 6. 推荐下一轮的三个任务

### A：把影子实验的记录做可信

实现请求—响应绑定、异常区域隔离、归档 schema/hash 一致性。保留 source-only 与不自动改 deck 的边界。

### B：把评测从标签扩展到拆分范围

以 P5 为强制反例：人工只编辑标题、保留仪表盘正文时，模型把 KPI/表格/图表内部都原生化，不能记录为“完整方案一致”。

人工记录区分 proxy、明确人工标注和试编译后否决；调参使用的区域不再冒充独立测试样本。不要为追求一致率把人工决定喂给模型。

### C：打通三个区域的候选试编译

- P5：标题可编辑，仪表盘主体明确保留。
- P8：对当前保真优先目标，原图方案与 hybrid 作为两个候选，记录否决原因；有不同编辑目标时允许重新评估。
- P12：数值证据可核对的条形图，明确是形状级编辑还是数据驱动图表编辑。

然后增加不同模板的新区域，记录首次提案、试编译后接受、人工否决、有效编辑收益、失败和完整成本。不急着新增编排框架。

## 7. 隐私与实验边界

“不发送 OCR 文本”不等于“不发送图片里的文字”。裁图本身可包含业务内容；原始响应不提交 Git 也不等于没有外发。

建议由调用入口明确允许的模型端点和可外发材料范围，使用授权或合成/脱敏样本。当前 review 不对服务提供方的数据政策作未经核验的推断。
