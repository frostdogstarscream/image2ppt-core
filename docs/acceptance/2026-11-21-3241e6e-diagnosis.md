**一次批调用最多是 6 次实际 Office 检查。** 正式候选首次验证一次，加最多两轮隔离，一共 3 张检查票。远端每张票先运行一次 check_local，只有 UNKNOWN 且 QA_INFRASTRUCTURE_UNAVAILABLE 才再运行一次，因此上界为 3×2=6。第二次检查仍返回 UNKNOWN 就不会进入依赖 REVIEW_REQUIRED 的下一轮。单机直接调用的对应上限是 3。缓存命中可降为 0。这里的“一次”指整套 Office 检查，每套内部又会多次打开、修改、保存、重开文档。见 runtime/service.py:578–612、770–809；runtime/office_bridge.py:108–142。

**同一对象跨 Agent 两轮的上界是 12，而非一次 batch 的上界。** host_evidence.py:150–162 按目标 ID 筛选，至多两轮，第一轮须已有提交进展才允许第二轮。service.py:149–163 在一次工具返回后记录一轮，commit 才回写 progress。不同对象、宿主直接调用、最终整页验证不受这个乘积的全局约束。隔离每张未缓存的票都会走 service.py:792 的 office_validations 预留；同票 worker 内部重试未另扣。批次回复列 auto_repaired_frame_ids 和 isolated_dropped_ids，但没有逐轮 isolation_history、物理 office_attempts（batch_backbone.py:1973–2008）。首次失败目录在 worker 本地 output 的同级，只有 output 打包回传，不能从服务器完整重建两个物理尝试（office_bridge.py:118–142）。

原始 J/request.json 的 runtime_seconds 和 adaptive_budget.max_seconds 均为 7200，Office 额度为 60，Agent 步数为 64。远端 submit 单票等候上限默认 1800 秒（office_bridge.py:50–72），两次物理尝试共享这一张票的等候窗口。单个 batch 仅三张票即可占用至约 5400 秒的等候，两轮约 10800 秒，未加编译或排队以外的开销，故不能保证在两小时内跑满上界。此为上界估算，并非历史耗时。runner.py:150、166 和 app.py:93 有任务截止机制；state.py:46–50 从 session 读取剩余时间。原始三个操作的 completed.json 均记录 remaining_seconds=null；不能据此断言没有宿主总超时，也不能认为每次 Office 启动前已验证足够的剩余时间。

**photo_frame。** service.py:345–366 构造 kind=batch、isolation_attempted=True，但没有 batch_spec。旧版在外层因这个布尔值跳过；3241e6e 在 REVIEW_REQUIRED 时会进入 restage_batch_candidate_subset，因无 spec 在 batch_backbone.py:1571–1573 立即返回 False。现有构造器不会实际重排照片框，仍可能触发同票 worker 的基础设施重试。若今后加上 spec，这个布尔值的含义已变成“此前已尝试”，会将再次出现的改框建议转入剔除项（:1577–1580），不是可靠的禁止隔离开关。
